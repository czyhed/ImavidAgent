# 未确认的提交直接失败并可重试，不再“待核实”（局部取代 ADR-0005 的 unknown 规则）

日期：2026-10-28。决策人：用户（「取消这些核实功能，直接跑就可以」）。

背景：生产中 5 条视频运行停在 `unknown`（`UPSTREAM_UNKNOWN`，无上游编号），3 条停在 `cancelling`。两者都属于活跃状态，占住节点：预览变为 recover / 阻塞，批次等待，界面出现「待核实」与「核实」按钮，项目无法继续。

决定（创作 v2 的生成运行，覆盖 ADR-0005 与 AGENTS.md 中「unknown 只查原任务」）：

- 不再产生、也不再展示 `unknown`。提交后没有确认的上游编号（网络错误、超时、HTTP 5xx、响应缺任务编号、图片同步响应丢失）→ `failed`，错误码 `SUBMIT_UNCONFIRMED`，提示「提交未确认……可直接重试；若供应商实际已受理，可能多计一次费用」。失败不是活跃状态，用户一次点击「重试」即可新建请求；系统不自动重提。
- 已有上游编号：查询出错保持 `running`，tick 持续自动查询；自最近一次成功查询起连续失败超过 30 分钟 → `failed`，错误码 `POLL_FAILED`。起始时间存在 `output._pollFailSince`（不对外返回，无结构迁移）。
- 取消：无上游编号 → 立即 `cancelled`；取消接口出错 → 仍本地标记 `cancelled`，忽略上游后续结果；任何运行不得在 `cancelling` 停留超过一个 tick。
- 历史数据在 tick / drive 中规整（非破坏性迁移）：`unknown` 无编号 → `failed`；`unknown` 有编号 → `running`；无编号 `cancelling` → `cancelled`。
- `recover` 路由仅为兼容保留：触发一次轮询或空操作。

代价：供应商实际已受理时，重试可能多计一次费用；已在提示中说明。仍不自动换模型、不自动付费重试；有上游编号的运行仍只查询原任务，不重提。

诊断：提交 / 查询失败各输出一行 `video-submit-error` / `image-submit-error` / `poll-error`，含运行编号、错误码、上游 HTTP 状态与原因名称；不记录响应体、素材、提示词或密钥。视频提交超时 300 秒，其余请求 120 秒。
